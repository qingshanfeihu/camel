          1. 主决策字段

          这几项决定一条记录最终被归到哪类 action，以及要挂到哪条树路径。

          action
          最终动作决定落在第二层哪一支：discard / merge / needs_tree_session / tree_create_*。
          target_node_id
          目标节点或父路径merge 直接并入已有节点；tree_create_* 里通常表示建议父路径。
          target_block_id
          源块定位用于回到原始 chunk，对照具体哪一段文档被裁决。
          tree_level
          树层级leaf / branch / trunk，帮助判断 action 与层级是否一致。

          2. 聚合辅助字段

          这些字段不一定是最终落盘目标，但会影响“第三层桶”怎么显示。

          enrich_fields.parent_candidate
          父路径候选tree_create_* 会把它和 target_node_id 合并，取更完整的父路径作为聚合键。
          entity_title
          块标题便于人读，但不是决策树第三层分桶键。
          source_file
          文档来源Inspector 里会统计一个 bucket 来自哪些文件。
          source_evidence
          裁决理由能直接看出是 LLM 决策、规则命中，还是 validator 重写。

          3. 扩展补丁字段

          chunk_meta_patch 里是后续农民真正要消费的结构信号，Inspector 会把常用子字段展开给你看。

          product_module
          产品模块例如 SLB / 基础网络 / 安全，是树父路径判断的重要旁证。
          command_prefix
          命令前缀帮助判断 leaf 是否真是 CLI 命令，而不是功能说明。
          chunk_type / step_type
          块类型single_command / narrative / health_checks 等，辅助判断 leaf/branch。
          function_hierarchy
          功能层级信号若能推出 branch 路径，validator 会优先把 leaf 修正到具体父节点下。

          按 action → 聚合键 → 样例字段

          支持：滚轮缩放 + 鼠标拖拽平移；点击 action / 聚合键节点可同步刷新 Inspector
          根：当前源文件总条数 二层：action 分支 三层：真正分桶字段（不是 entity_title） Inspector：展示 bucket 内样例记录的字段结构
